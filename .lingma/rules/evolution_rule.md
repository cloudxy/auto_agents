# 架构演进规则

> 当涉及架构设计、分层、解耦时，遵循本规则。具体执行时查找对应 Skill。

## 核心价值观

| 信条 | 含义 |
|------|------|
| 配置即代码 | 硬编码是技术债，配置必须外置、版本化、环境隔离 |
| 日志即证据 | 没有日志的执行等于没执行，关键路径必须留痕且可追溯 |
| 独立部署优于耦合 | 能独立运行的就不要捆在一起，边界清晰才能独立演化 |
| 面向接口而非实现 | 依赖抽象让替换成为可能，依赖实现让重构成为灾难 |
| 数据流向不可逆 | 请求单向流动，禁止反向穿透，循环依赖是架构腐败的起点 |
| 模型即契约 | ORM 模型是数据库契约，Pydantic 模型是接口契约，二者不可混用 |
| 爬取与存储分离 | 爬虫只负责采集和清洗，不负责持久化——存储是后端的事 |
| 反爬是生存底线 | 没有反爬策略的爬虫不是爬虫，是 DDoS |
| 数据质量先于数量 | 100 条干净数据 > 10000 条脏数据 |

## 设计原则

### 分层

分层的本质是**约束依赖方向**。每一层只关心自己的职责，只调用下一层，永远不反向穿透。

判断标准：如果删除某一层，上层应该只失去一种能力（如存储能力），而不是全部崩溃。

### 解耦

耦合的代价不在今天，在明天。当你想替换 MySQL 为 PostgreSQL，想用 Kafka 替代 Redis 队列——耦合越深，改动越痛。

**解耦边界**：
- **数据边界**：不共享数据库表，通过 API/MQ 传递数据
- **依赖边界**：不直接 import 对方内部实现，通过接口交互
- **部署边界**：可独立启动、扩缩容、故障隔离

### 演进

本项目采用多项目架构，各子项目技术栈独立、依赖独立、可独立部署。

演进方向：爬虫通过 Redis/MQ 发送数据 → 引入消息队列解耦 → 微服务化
