## 1. 背景与问题定义

四套 Working Backwards（①–④，2026-09-10）+ 一套 Wave A 增补（§1.5，2026-09-11）。③ 是用户能 **做** 的事。无生产工单；证据 = 本机活体 + 代码/诊断（2026-09-10）+ 操作者反馈 file:line 核对（2026-09-11）。

### 1.1 满额与付费出口

**谁**：用量已经顶到上限的租户负责人（owner / 公司管理员）；被拦住却不能改套餐的只读成员。

**现在什么情况**：满额主 CTA 已离开注册（v2 已兑）。官网专业/企业仍「预告不可购买」。用量同一屏既写「本波不提供自助改套餐或支付」又提供「提交升级订单」。租户提交后 **没有** 自己的订单列表。只读点申请拿到内部码口吻，不是「找管理员」。在线支付空（符合 Q-BILL）。专业档对外数字与账本不是同一套。

**期望什么结果**：「满了知道下一步。官网和后台说的是同一件事。我能看见自己那张线下申请。我改不了套餐时，页面让我去找管理员，而不是甩一个内部码。在线支付还没开通——这点不要骗我。」

**凭什么说改善了**：官网定价 / 用量满额 CTA / 后台订单入口不得互否、不得「当前可买」可抽检；租户能列出本企业订单（含确认后已确认）。**FR-50 完成停在「我的订单能看见已确认」。** 只读可见句不含内码；在线渠道 0 笔任何单。官网动词、确认后是否履约专业档三数字、是否撤 ¥299 **不**当成本波已选解法。

### 1.2 两把租户钥匙

**谁**：要把结果拉进自家系统的采集经办；要把渠道组令牌接到常见中转站客户端的负责人。

**现在什么情况**：出站拉数仍 401，无自助签发（FR-13 拒绝已兑）。后台能签发渠道组令牌，但没有 Base URL/用法、`used` 恒 0、令牌打不到平台网关。官网企业档仍把渠道组当预告。词汇表还写「令牌不发给租户」。两把钥匙都叫令牌。

**期望什么结果**：「我能自己发一把拉数的钥匙，只能拉我们公司的条。渠道组令牌签发后我知道贴到哪、发出去用量会动。值班仍管总闸，我改不了。官网不得写成当前可买中转。」

#### FR-93 软删用户：可筛「已删除」、超管可恢复、标识可释放

操作者已决（F3）：被删用户通过筛选项可见，超管可恢复（软删为真）。恢复必须处理 username/email 占用冲突；软删行对标识的占用语义由「永久占用」改为「可释放」。**占用判定各自独立：username 与同租户在册用户冲突、email 与全局在册用户冲突，任一冲突即恢复拒绝**（GWT-93.4；可释放拆格见 GWT-93.5/93.7）。恢复仅平台超管；用户管理是平台页（租户不可见，FR-82 语义保持）。

| GWT | 类型 | 内容 |
|---|---|---|
| GWT-93.1 | 正常·筛已删 | **Given** 平台超管打开用户管理，存在 ≥1 个软删用户 **When** 选择筛选「已删除」 **Then** 列表出现这些用户且带已删除标记；活跃用户不出现在该筛选结果中 |
| GWT-93.2 | 边界·默认视图 | **Given** 存在 ≥1 个软删用户 **When** 超管观看未选「已删除」的默认列表 **Then** 已删用户不出现（既有行为保持） |
| GWT-93.3 | 正常·恢复 | **Given** 「已删除」筛选中某用户，其 username/email 未被占用 **When** 超管点恢复 **Then** 该用户出现在默认列表且状态=启用；「已删除」筛选不再出现该用户；上报 `user_restored`（GWT-92.8） |
| GWT-93.4 | 边界·占用冲突 | **Given** 已删用户 U 的 username/email 已被某个现有活跃用户占用 **When** 超管对 U 点恢复 **Then** U 保持已删除（仍在「已删除」筛选）；超管看见中文说明「用户名或邮箱已被现有用户占用」；现有用户的标识与数据不变。占用语义各自独立：username 按同租户在册判、email 按全局在册判，任一冲突即本句拒绝 |
| GWT-93.5 | 边界·username 占用可释放 | **Given** 已删用户 U 原属租户 T，其 username 在租户 T 内未被任何在册用户占用（email 是否占用不影响本格判定） **When** 超管在租户 T 用同一 username 新建用户 **Then** 创建成功（已删行不永久占用 username）；U 仍留在「已删除」筛选 |
| GWT-93.6 | 越权 | **Given** 租户任一角色 **When** 直打用户管理或恢复动作 **Then** 与「页面不存在」同形；已删用户保持已删除（注：GET /admin/users 列表面维持既有 require_admin（r13 金标，列表限本租户行）；同形语义由平台页守卫+恢复动作面兑现——IMPL-QA-3 裁决，见 contract §7.9） |
| GWT-93.7 | 边界·email 占用可释放 | **Given** 已删用户 U，其 email 未被任何在册用户全局占用（username 是否占用不影响本格判定） **When** 超管用该 email 新建用户 **Then** 创建成功（已删行不永久占用 email）；U 仍留在「已删除」筛选 |
| GWT-93.8 | 边界·再恢复 | **Given** 已删用户 U 的 username 或 email 已被在册用户占用（含经 GWT-93.5/93.7 释放后被新建用户占用的情形） **When** 超管对 U 再次点恢复 **Then** 与 GWT-93.4 同句：U 保持已删除、中文占用说明、占用者的标识与数据不变 |
| GWT-93.9 | 边界·重复恢复 | **Given** U 已恢复为启用（在默认列表，「已删除」筛选无 U） **When** 超管再次触发对 U 的恢复 **Then** U 状态保持启用；不重复上报 `user_restored`；不产生任何新的恢复副作用 |

## 3.1 状态流转

### 线下升级申请（FR-50）

```
（无单）──负责人/公司管理员提交──> pending（待确认收款）──超管确认收款──> paid（已确认）
在线渠道提交 ──不产生任何单──> （无新单；原 pending 若有则保持）
已有 pending 再提交 ──不产生第二张──> （原 pending 保持）

终态：paid（确认收款不可逆）
本波无取消、无退款（§5）
```

| 流转 | 触发条件 | 谁能触发 | 副作用 |
|---|---|---|---|
| 无单 → pending | 提交升级申请（档位=账本已有付费档，本波仅 pro） | 负责人、公司管理员 | 本企业多一条待确认申请；配额不变 |
| pending → paid | 确认收款 | 仅平台超管 | 申请变为已确认；记确认时刻。配额是否履约为定价页该档三数字 = Q-PRICE，本表不冻履约 |
| 在线渠道 | 选在线支付 | 负责人、公司管理员 | **不产生任何单**（含不产生 pending）；用户见未开通句 |
| 已有 pending 再提交 | 用量页再次点提交升级申请 | 负责人、公司管理员 | 不产生第二张；原 pending 保持；配额不变 |

**非法流转**（`/qa` 负向来源）：

| 非法流转 | 期望行为（状态 / 记录 / 副作用） |
|---|---|
| 租户确认 pending | 保持 pending；配额不变 |
| 只读 / 经办提交 | 不产生申请；见找管理员 |
| paid → pending | 保持 paid |
| paid 再确认 | 保持 paid；不叠档 |
| 提交档位=免费的升级申请 | 不产生申请；说明免费档无需下单（用户可见中文，不含内部码）。**不是**「从免费升专业」（GWT-50.2） |
| 提交企业档升级申请（本波无 SKU） | 不产生申请；不得假装账本有第三档（GWT-50.14） |
| 夹具两张 pending 都确认 | 两张均为 paid（不可逆）；配额不因第二张再叠一档（GWT-50.16） |

此表与后续 `db-spec` 第 2.1 节冲突时 **以本文为准**（业务规则归 PM），塑形时显式同步。

### 用户软删与恢复（FR-93，Wave A 增补）

