# 产品深层次问题审查（独立视角：客户旅程）

- 审查日期：2026-09-06
- 审查透镜：访客 → 注册 → 激活 → 付费 → 续费/流失 的完整客户旅程
- 审查范围：frontend/official + frontend/admin、backend/app + backend/services + backend/tasks、platform_core、config/、根文档（README/CONTEXT）、docs/adr（决策事实参考）。未阅读 .sdlc/.scratch/docs/plan/docs/research。
- 审查基础：仅依据仓库代码与文档事实，无外部先入信息。

---

## 总体判断

这个仓库的工程治理水平（租户行级隔离、配额服务、用量看板、运营台）明显高于它的**商业完成度**：它做成了「多租户爬虫工作台」，但没做成「SaaS 生意」。客户旅程在两端断裂——入口端，定价页卖着三档套餐，系统里却不存在任何支付/订单/订阅/套餐 SKU 概念，升级的唯一路径是平台超管手工编辑配额 JSON；执行端，三档套餐最核心的卖点维度（LLM tokens/月）有计量、有看板、唯独没有执行闸门，租户级 token 配额检查函数在整个调用链上零调用。对外数据 API 游离于租户体系之外（平台级静态 Key + 无租户过滤），既是隔离漏洞也是无法计价的变现缺口。生命周期管理单向且半成品：到期巡检会置 expired，但登录链路根本不校验租户状态，UI 宣称的「到期拒绝登录」未兑现。此外，注册后没有引导、第一个任务强依赖用户无法自控的 Worker、到期/流失/退出口全部依赖人工。结论：**当前形态是一个「给内部运营用的平台」而不是「给客户自助用的产品」，商业化短板不是缺某个功能，而是「客户承诺」与「系统执行」之间系统性脱节。**

## 深层次问题清单（按严重度排序）

### 1. 有定价页、无交易层：三档套餐在系统中零落地，付费转化 100% 依赖人工

**严重度：高**

**证据**
- `frontend/official/src/pages/Pricing.tsx:10-29`：免费 ¥0 / 专业 ¥299/月 / 企业定制三档；专业档 CTA「联系升级」、企业档 CTA「联系销售」，但 `L15/21/27` 三者 `href` 全部指向 `/register`——注册后落入免费档，与「升级/销售」毫无衔接，且页面上没有任何真实联系渠道（邮箱/表单/电话）。
- 全库 grep `billing|payment|subscription|订单|支付|账单|invoice`：除 `platform_core/exceptions/business.py:9` 的注释举例（「订单数量不合法」）外零命中——无支付网关、无订单/订阅/发票模型。
- `platform_core/models/tenant.py:9-26`：租户表无 plan/tier 字段，「套餐」在数据模型中不存在，只有裸 `quota` JSON。
- `frontend/admin/src/pages/PlatformOps.tsx:43-61, 215-231`：所谓「调整套餐」= 平台超管在 Modal 里手填三个数字（并发/存储/tokens）+ 手选到期时间。
- `backend/services/tenant_admin_service.py:75-96`：`patch_tenant` 直接深合并 quota JSON，无套餐模板、无价格、无周期、无台账。

**为什么是深层问题**
SaaS 的付费闭环由「价格锚点 → 意图表达 → 支付/合同 → 权益变更 → 留痕」组成。本系统只有第一个和最后半个（权益变更留了审计日志）：中间三环全靠「客户找到联系方式 → 人找平台管理员 → 管理员手填数字」。这意味着：定价页每一行承诺都需要一个人肉流程兜底；升级收入规模直接受限于运营人力；且无价格台账，客户争议（「我付了钱为什么还是 5 并发」）无对账凭证。这不是缺一个支付按钮的功能缺失，而是商业模型没有进入系统的结构性缺口。

**解决方案**
分两阶段做最小交易闭环：
1. 第一阶段（不接支付，先把「人工动作产品化」）：新增 `plans` 表（SKU：名称/价格/周期/quota 模板/权益说明）+ `tenants.plan_id`；把 Pricing 页两个 CTA 改为「升级申请单」（租户内提交，选择目标档位 → 进入平台运营台的申请队列 → 运营确认收款（对公/扫码截图留档）→ 审批通过自动套用 plan 的 quota 模板 + 自动续 `expires_at`，全程审计）。取舍：不自建计费引擎，接受「申请-审批-人工收款-台账」的半自动形态；月度自动扣费在支付渠道稳定前明确不做（避免自动续费合规风险）。
2. 第二阶段：接入聚合支付（个人：微信/支付宝 Native；企业：对公 + 电子合同），订单表驱动 quota 变更，审批环节降级为异常处理。

### 2. 租户 LLM token 配额「有计量、有看板、无执行」：定价核心卖维是空头支票，且全局熔断池使租户互相牵连

**严重度：高**

**证据**
- `backend/services/quota_service.py:119-135`：`check_llm_tokens_month`（租户级 429）**定义完整但全库无调用点**（grep 仅命中定义与测试）；对照 `check_task_concurrency`（`spider_task_service.py:173`）与 `check_result_storage`（`tasks/consumer.py:694`）均有真实调用。
- `backend/services/ai_planner/llm_client.py:288, 320-334`：LLM 调用的预算熔断读数 `get_month_used(usage_dim, tenant_id)`，但判断阈值 `budget` 来自**全局配置** `LLM.MAX_TOKENS_BUDGET`（`config/default/llm.yml:19` = 200000），熔断维度是 `usage_dim`（`provider:<id>` 或 `config`），即**所有租户在平台公共供应商上共享一个全局 20 万 tokens/月的池子**，谁都不看租户自己的 `llm_tokens_month`。
- `frontend/admin/src/pages/Usage.tsx:46-63`：用量看板展示「LLM Token（本月）X / 配额 Y」进度条——但该配额在执行链路上不存在，仪表盘对用户撒谎。
- `frontend/official/src/pages/Pricing.tsx:19`：专业档卖「500 万 LLM tokens/月」——即使运营台把某租户 `llm_tokens_month` 配成 500 万，调用路径也不会读它；且全局 20 万熔断先于该配额触发。
- 连带风险：免费档承诺「平台公共 LLM 供应商（兜底）」（`Pricing.tsx:14`），一个重度租户可以把全局 20 万池烧干，导致**所有租户**的 AI 采集同时熔断。

**为什么是深层问题**
「卖的维度」与「执行的维度」错位是 SaaS 定价失效的根源：tokens 是三档套餐的区分维度之一，却在执行面不可售卖、不可隔离；同时唯一真实的护栏（全局 20 万）是一个共享池，制造了无定价支撑的租户间负外部性。这不是 bug，是「计量系统」与「计费系统」从未对齐的系统性缺口。

**解决方案**
1. 在 `llm_client.py` 预算检查处（约 L323 附近）并行调用租户配额闸门：读数直接复用 Redis 月度 hash 的租户维度（`llm_usage_service.py` 已按 `tkey|dim|model|metric` 记账，无需 DB COUNT），超限抛业务异常（429 语义，文案指向 BYOK 配置或升级入口）；fail-open/fail-closed 复用已有 `LLM.BUDGET_FAIL_CLOSED` 开关。
2. 明确计量口径：**平台公共 provider 的消耗计入租户配额；BYOK（租户自建 provider）不计配额、仅计展示**——与专业档「自有 Key」卖点一致，避免向不产生平台边际成本的用量收费引发抵触。
3. Usage 看板读数与执行闸门同源（同一 Redis hash），消除「展示口径 ≠ 执行口径」。
4. 平台公共池的容量按「Σ 活跃租户配额」预算化管理并接监控告警，避免共享池雪崩。取舍：闸门前置会给每次 LLM 调用加一次 Redis 读（微秒级，可接受）；若追求极简可只在 AI 采集入口（planner）而非底层 client 做闸门，但底层做更防绕过。

### 3. 对外数据 API 游离于租户体系之外：平台级静态 Key 可跨租户读全量结果，且该变现点无法计价

**严重度：高**

**证据**
- `backend/app/external_api/v1/public.py:26-34`：`_require_api_key` 校验 `X-API-Key` 命中 `EXTERNAL_API.API_KEYS`——**平台级静态配置**（`config/default/external_api.yml:3-8`，`API_KEYS: []`，经环境变量注入），不是租户资源：无按租户签发、无吊销、无归属、无调用计量。
- `public.py:37-88` → `spider_query_service.query_public_results:91-117` → `spider_result_repository.query_by_spider:131-161`：查询链路**无任何租户过滤**；且 `/data/{spider_name}` 不传 `spider_name` 即跨任务全量查询（`repository:141-143`「跨任务全量查询」）。
- 隔离机制事实：`platform_core/tenant_context.py:134-160` 的行级隔离是 ORM 事件钩子，仅在**有租户上下文**时注入 `tenant_id` 过滤；外部 API 请求无 JWT、无租户上下文 → 无过滤 → **一个静态 Key 可拉取所有租户的采集结果与聚合统计**（`public.py:136-143` `/stats` 同理）。

**为什么是深层问题**
「API 数据服务」是采集类 SaaS 最自然的二次变现点（按调用量/API Key 分档计费），本系统把它做成了「管理员配的一个共享密码」：客户拿不到 Key（要找运营），平台收不了费（无计量），出事无法追责（无归属审计），且天然违反多租户承诺（A 租户的数据可被持有共享 Key 的 B 方拉走）。对 SaaS 而言，「数据隔离承诺」与「对外 API 现实」的矛盾会在第一个企业客户的安全问卷上直接爆雷。

**解决方案**
1. 新增 `api_keys` 表（`key_hash`/`tenant_id`/`scope`/`rate_limit`/`expires_at`/`created_by`/`revoked_at`），后台自助签发与吊销（展示一次明文，落库哈希）。
2. external_api 鉴权后以 key 归属注入 `tenant_scope()`，行级隔离钩子自动生效——不需要改查询链路，这是本仓库现成机制的直接收益。
3. 按调用次数记账（Redis 计数 + 日聚合表），为后续按量计价留数据。
4. 迁移期：旧 `EXTERNAL_API.API_KEYS` 语义收窄为「平台运维 Key」，文档标注 deprecated 并给出截止版本。取舍：多一次 Key→租户的查表（可缓存 Redis），换取隔离、计量、可售三重收益。

### 4. 到期生命周期只做了一半：expired 实际不拦截任何请求，「到期生效」是宣称而非事实；到期前无提醒、到期后无挽回

**严重度：高**

**证据**
- `backend/services/tenant_expiry_service.py:21-36`：每小时巡检 `expires_at < now` 置 `status=expired`——降级动作本身存在。
- 但登录链路不校验租户状态：`backend/services/auth_service.py` `authenticate`（约 L93-141）只验用户密码与 `is_active`，不 JOIN tenant 查 `status`；`backend/app/middleware/tenant_context.py:91-125` `dispatch` 只复核用户身份/平台态，同样不查租户状态。grep 全登录/中间件链路无 `tenant.status` 检查——**expired 租户的用户照常登录、照常跑任务**。
- `frontend/admin/src/pages/PlatformOps.tsx:202` 明确宣称「到期租户会被登录拒绝（可行动文案）」——宣称与实现不符。
- 到期前提醒：`notify_service.py` 仅任务完成通知（webhook/email/钉钉/企微），无「到期前 N 天提醒」；到期后无自助续费（见问题 1），无宽限期/只读期，无降级路径，无流失挽回动作。
- 数据保留：expired 租户的 `spider_results` 等数据无归档/清理策略（`grep retention|清理` 无租户数据生命周期代码），存储成本随流失租户线性累积。

**为什么是深层问题**
到期管理是续费收入的第一现场。现状是三重失效：技术上不生效（宣称拦截但实际放行，运营以为降级了、其实没有）；商业上无抓手（到期前不打扰、到期后无自助续费，流失是默认结局）；成本上无回收（流失租户数据永久占存储与结果配额池）。到期巡检每小时跑一次，跑的是一个不产生任何业务后果的写操作。

**解决方案**
1. 补齐执行闸门：`authenticate` 命中后 JOIN tenants，`status != 'active'` → 403 + 可行动文案（「套餐已到期，请联系续费或访问续费入口」，问题 1 的申请单可复用）；同时在 `tenant_context` 中间件按 DB 复核（防存量 token 绕过）。
2. 生命周期从「硬切换」改「宽限带」：`expired` 后 14 天只读（可登录、可导出、禁提交任务）→ 之后 `disabled` 拒登；到期前 7/3/1 天经 notify_service 邮件触达 owner（SMTP 通道现成）。
3. 数据保留定档：`disabled` 后 90 天归档（`platform_core/models/archive.py` 已有归档模型）后清除，写入对外《数据保留与归属》文档。取舍：只读宽限期牺牲一点「立即止血」的强硬，换取续费转化窗口——对 ¥299/月量级的自助客户，宽限带来的挽回价值远大于风险。

### 5. 激活链路断裂：注册成功无登录引导、首次价值强依赖用户不可控的 Worker、共享队列无租户公平性

**严重度：高**

**证据**
- `frontend/official/src/pages/Register.tsx:48-57`：注册成功页只有「再注册一家」和「返回官网」两个动作——**没有「去登录」**，未告知后台地址（官网 9113 与后台 9112 分离）；新 owner 拿到的是邮箱前缀截断的用户名（`tenant_signup_service.py:61`），登录该用邮箱还是用户名需自行摸索（`LoginRequest` 两者语义未在注册页说明）。
- 首任务依赖：`README.md:414` FAQ 第一条「任务一直 pending = Worker 未启动，另开终端 `run.py spider`」——SaaS 客户没有服务器终端；Worker 是平台全局资源，租户只能等待且看不到原因（「节点监控」页是平台运维视角，租户无从判断容量）。
- 公平性：`backend/tasks/consumer.py:215-233` `_dispatch_loop` 全局单队列 blpop，无全局并发上限、无租户加权——配额只限制单租户自己的 pending/running 数（`quota_service.py:80-98`），多租户合计对共享 Worker 的挤占无治理；企业档「不限并发（协商）」（`Pricing.tsx:25`）在共享队列模型下等于承诺一个租户可以合法占满全平台算力。

**为什么是深层问题**
价值时刻（time-to-value）决定免费到付费的转化：注册 → 登录 → 建任务 → 等 Worker → 拿数据这条链上，第二环无引导、第四环不可控且无预期管理。更结构性地，共享算力是本产品最贵的平台成本，而它既没有容量规划（全局并发上限）、也没有分配策略（公平性）、也没有与售卖档位对应（企业档承诺与共享池矛盾）——「卖出的并发」与「实际可调度的并发」是两个没有对过账的数字。

**解决方案**
1. 注册成功页改为行动导向：主按钮「进入控制台」（携带 `tenant_slug` 深链后台登录页——`auth.py:61` 的 tenant_slug 字段正好从预留转为消费或彻底删除），次按钮返回官网。
2. 首屏 onboarding：Dashboard 对零任务租户渲染三步引导卡（提交任务 → 观察日志 → 导出结果）；任务 pending 超 2 分钟时任务列表内嵌提示「平台调度中」+ 帮助链接，把 Worker 依赖转译为用户语言。
3. 调度治理分两步：先加**全局并发上限**配置 + 租户 pending 占用上限告警（防打穿）；再做**分租户队列轮询**（scrapy-redis 按 tenant 前缀分队列，dispatch 轮询加权取任务），企业档兑现为「专属队列」而非「不限并发」——把不可兑现的承诺换成可交付的隔离。取舍：分队列增加调度复杂度，若当前租户数 < 10 可先只做全局上限 + 企业档暂停售卖。

### 6. 账号信任链缺失：注册无邮箱验证、owner 无自助找回密码、双注册入口与 default 共享池语义混乱

**严重度：中**

**证据**
- `tenant_signup_service.py:34-53`：企业注册仅做字符串校验，**无邮箱验证**（无验证码/确认链接）；任何人可用任意邮箱成为某「企业」的 owner。
- 自助找回密码：全库唯一重置路径是 owner 给成员重置（`members.py:86-96`）；owner 本人忘记密码无邮件重置流程，唯一途径是服务器上跑 `backend/scripts/set_admin_account.py`（`README.md:404`）——单管理员租户一次忘密码即彻底失联，且需平台运维登服务器解救。
- 双注册入口：官网企业注册（`/tenant/signup` → 独立租户 owner=admin）与后台 API `/auth/register`（`auth_service.register_user:129-187` → 挂 **default 租户**、`tenant_role=viewer`）并存；所有个人注册用户共享 default 租户的配额池（`quota_service` 按 tenant_id 计数），一个 default 用户跑满并发，其余个人注册用户全部排队——用户之间互不相识却共享资源上限。

**为什么是深层问题**
信任链缺失（无验证邮箱）在 SaaS 是合规与滥用的双重敞口：免费档的 5 并发 + 20 万 tokens 可以被脚本批量注册无成本套取（IP 限流 `rate_limiter` 只能减缓不能阻断，且邮箱零成本）。找回密码缺失则把「人工介入」埋进了最低频也最致命的环节。default 共享池是一个语义模糊的准公共租户：它有配额、有 owner 吗、谁来付它的账单？——这些问题现在都没有答案。

**解决方案**
1. 邮箱验证：注册后发确认邮件（复用 notify_service 的 SMTP 通道），24h 未验证禁用登录；取舍上可对免费档保留「验证前可登录体验但禁提交任务」以减小摩擦。
2. 自助找回：邮件重置 token（单次、15 分钟有效）+ 重置后全设备 token 失效；这与邮箱验证共用同一套邮件基建，属一次开发两处收益。
3. 收口注册语义：下线 `/auth/register` 公开个人注册（或改造成「凭邀请码加入租户」），default 租户退化为纯系统占位（禁登录新注册），消除共享池。取舍：牺牲「个人玩家」入口换语义清晰；若保留个人赛道，应让个人注册也走轻量租户（一人一租户，配额独立）。

### 7. 定价维度与成本维度错位：最大边际成本（任务执行）不计价，最小成本维度（BYOK tokens）被售卖

**严重度：中**

**证据**
- 配额三维度 `task_concurrency / result_storage / llm_tokens_month`（`quota_service.py:24-28`）：**任务执行次数不在其中**——只要并发 < 5 且存储未满，免费租户可无限次提交任务；而每次任务的 Worker 计算时间、代理流量、目标站点风控消耗是平台最真实的边际成本。
- 专业档卖点「自有 LLM Key（BYOK）」（`Pricing.tsx:20`）：BYOK 的 tokens 由租户自己的供应商账户结算，平台计量（`llm_usage_service` 支持 provider 维度）但不产生自身边际成本——把它包装成「500 万 tokens/月」卖的是平台不需要付出的成本。
- 企业档「不限并发（协商）」：见问题 5，与共享 Worker 容量模型冲突。
- LLM 公共兜底（免费档）是唯一真实的成本敞口（问题 2 已述：且当前连租户级护栏都没有）。

**为什么是深层问题**
SaaS 毛利取决于「售卖维度随成本维度同步增长」。本产品成本随「任务数 × Worker 时长 × 代理流量」增长，售卖却卡在并发/存储/token 三个都不随任务次数增长的维度上——重度用户（跑 10 万次小任务）对平台成本贡献最大、付费压力为零；轻度用户反而被存储配额卡住。这会系统性筛选出「最亏钱的用户」，定价页越成功，亏损越快。

**解决方案**
1. 增加第四配额维度 `task_runs_month`（月任务执行次数）进入 `quota` JSON、Usage 看板与三档 SKU（免费 100 次/专业 5000 次/企业协商）；`check_task_concurrency` 的调用点（`spider_task_service.py:173`）旁并列校验，实现成本低（同文件同模式）。
2. 重构专业档价值叙事：卖点从「tokens 额度」改为「BYOK 免费 + 更高执行次数 + 成员/用量治理」，tokens 额度仅描述平台公共兜底部分。
3. 企业档交付物定义为「专属 Worker 池/队列」（问题 5 方案），把「不限并发」翻译成容量隔离承诺。取舍：存量租户 quota JSON 加默认键即可平滑迁移（`quota_of` 已做逐键合并兜底，向后兼容），无需数据迁移。

### 8. 合规与退出口零产品化：无租户注销、无自助全量导出、删除权无落地路径

**严重度：中**

**证据**
- grep `注销|删除租户|delete_tenant|data_export`：仅命中「不可删除租户 owner」（`member_service.py:152`）与迁移注释「删除=注销不复用 slug」（`025_softdelete_unique_recreate.py:17`）——租户级注销流程不存在（软删字段在 `SoftDeleteMixin` 上，但无触发面、无数据处置链）。
- 数据导出：租户仅有单任务结果 CSV/JSON 导出（`README.md:322`）；无租户维度全量打包导出（任务定义/模板/结果/日志），迁移出走（vendor lock-in 解除）无路径。
- expired/disabled 租户数据无保留与清理策略（同问题 4）；`llm_token_usage`、`operation_log` 等表无 retention 定义。
- 对外文档（README/官网）无数据归属、删除权、保留期任何承诺条目。

**为什么是深层问题**
企业客户采购 SaaS 的安全问卷必问三件事：数据存哪、怎么删、怎么走。当前三个都答不出——这不是「以后补功能」，而是企业档（定价页明确目标客群）从第一天就过不了采购门槛的问题；同时流失租户数据的无限期留存让平台在合规上只承担成本不获得收益。退出口缺失反过来抑制进门口：理性企业会因「进得来出不去」而不进来。

**解决方案**
1. owner 自助「导出与注销」入口：全租户数据异步打包导出（JSON/CSV zip，任务定义+结果+用量）；注销走申请单（同问题 1 基建）→ 平台审批 → 软删 → 90 天后按 `tenant_id` 物理清除（spider_results/tasks/llm_token_usage/operation_log 均含 tenant 维度或可关联）。
2. 产出对外一页《数据归属与保留政策》（保留期、删除时限、导出格式），上线「数据导出」功能后放官网 Footer。取舍：物理清除需与备份生命周期对表（备份里的旧数据无法即时删除），政策如实写「备份滚动周期 +X 天」即可，诚实优于含糊。

### 9. 资源库板块是「橱窗」不是「渠道」：访客无转化动作、资产无获取路径，四板块定位官网只表达了一块半

**严重度：中**

**证据**
- 官网技能广场 `SkillsSquare.tsx` 与能力广场 `Capabilities.tsx`：只读浏览 + 详情弹窗（SKILL.md 全文纯文本展示，`SkillsSquare.tsx:158-163`），**卡片与详情页均无任何 CTA**——没有「注册后使用」「导入我的租户」「安装说明」；访客看完资产详情后旅程戛然而止。
- 后台存在资产导入能力（`skill_import_service.py`、adapters 分发机制、CONTEXT.md「适配器」条目），但官网橱窗与租户内资产库之间零链接：看到（匿名）→ 获得（登录后台→资产目录→手动导入）两段体验完全断开。
- 产品定位四板块（SaaS/爬虫/中转站/资源库）：官网导航仅「技能广场/能力广场/定价/注册」（`SiteLayout.tsx:19-24`），首页全部内容为爬虫板块——**中转站板块对外零表达**（对外也确实难以表达，见 README:38 该板块是 new-api 外挂巡检器），资源库板块只有橱窗无交易；「四板块」对访客实际呈现「一板块 + 两个静态列表」。

**为什么是深层问题**
资源库是差异化卖点（数据采集 + 资产复用的网络效应），但橱窗设计使其既不能获客（无转化）也不能防止资产外流（SKILL.md 正文匿名全文可见，正文即核心资产本体——白嫖无需注册）。板块定位与页面现实之间缺的不是页面而是「动作设计」：橱窗里的每件商品都应该是转化入口。

**解决方案**
1. 资产详情 CTA 化：未登录 →「注册后导入本资产」（深链 `/register?next=/skills?import=slug`）；已登录（后台侧资产目录）→「一键导入本租户」（复用 skill_import 既有能力，前端按钮接即可）。
2. 正文保护：公开态只渲染正文前 N 行 + 结构化元数据（分类/评分/tier），全文登录后可见。取舍：降低匿名传播性换取注册转化与资产保护——对一个定位「资产库」的产品，资产即是库存，裸奔的库存卖不出价格。
3. 对外定位收缩或补全：要么官网补「中转站」板块页（讲清对客户的收益而非内部巡检视角），要么对外统一表述为「智能采集 + 能力资产」双板块，避免官网信息架构与产品定位长期两张皮。

### 10. 宣称与现实的系统性漂移：文档、预留字段、示意数据构成对内对外的多重不一致

**严重度：低**

**证据**
- `README.md:253`「自注册用户默认 operator」vs `auth_service.register_user:180` 实际 `tenant_role="viewer"`（且该入口挂 default 租户，见问题 6）——权限承诺与实现不符。
- `auth.py:61-63`：登录 `tenant_slug` 为「预留字段未消费」，但同名跨租户消歧（`authenticate` 多行候选机制）恰恰需要它——预留的方向与实际需要一致却未接通，客户无感、多租户同名用户登录体验存疑。
- `Home.tsx:31-35,182-185`：Hero 展示「128,000+ 任务 / 3.2 亿条数据」静态示意（已有小字标注，尚可），但后端 `/external/v1/stats` 已有真实聚合能力，官网却接不上（无鉴权设计导致不能接，问题 3 的连锁）。
- 定价页「配额可在租户管理台调整」（`Pricing.tsx:38`）——租户侧无任何自助调整配额的页面（只有平台运营台），文案暗示的能力不存在。

**为什么是深层问题**
单条漂移是小瑕疵，但漂移集中在「对外承诺」一側（README 权限、定价文案、Hero 数据）时，说明缺少「宣称必须有实现背书」的机制。对 SaaS 来说，对外宣称即合同：漂移积累到企业客户尽调阶段会转化为信任成本。

**解决方案**
1. 建立「宣称-实现」对照清单（对外文案的每一条承诺 ↔ 实现文件），随发版检查；本报告问题 1/2/4/5 的修复即消除其中最严重的四条。
2. `tenant_slug` 做减法决策：要么接入登录流程（作为同名消歧入参，与 `authenticate` 的多行候选机制对齐），要么删除字段——预留超过一个迭代周期的字段应视为技术债。
3. 官网统计卡接真实数据（问题 3 的租户化 API Key 体系落地后，可签发官网只读 Key 拉取 `/stats` 聚合），示意数据标注保留为兜底。
